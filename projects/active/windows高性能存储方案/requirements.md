# Windows 高性能存储方案 — 工业检测数据存储需求

## 项目目标

设计并实现一个面向工业车辆外观检测场景的**高性能、高可靠文件系统/存储引擎**，解决现有 NTFS 方案在长期运行中偶发卡顿、元数据碎片化、冷热数据管理等问题。最终方案需可与大厂私有化存储方案进行多维度对比（性能、可靠性、成本、可维护性）。

---

## 业务背景

### 场景描述

工业软件在检测工位对车辆外观进行多角度拍照，采集图像、点云、结构化元数据（JSON），并实时落盘。每隔若干分钟（2–10 分钟）进入一辆车。

### 数据模型

数据按**层级目录结构**组织，不同项目的层级深度可能不同，典型结构如下：

```
<ProjectRoot>/
└── <Vehicle_VIN_001>/             # 第1层：车辆
    ├── <Station_Front>/           # 第2层：拍照点
    │   ├── cam01_001.jpg          # 第3层：照片（可能多张）
    │   ├── cam01_002.jpg
    │   └── pointcloud.pcd         # 点云文件
    ├── <Station_Rear>/
    │   ├── cam02_001.jpg
    │   └── metadata.json          # JSON 元数据
    └── vehicle_summary.json       # 车辆汇总信息
```

### 文件特征

| 类型 | 典型大小 | 数量/车 | 覆盖写 | 可丢弃 |
|------|---------|---------|--------|--------|
| 图像（JPG/PNG） | 1–20 MB | 10–200 | 否 | 否 |
| 点云（PCD/PLY） | 50–500 MB | 0–5 | 否 | 部分可 |
| JSON 元数据 | 1–100 KB | 5–50 | 可能 | 否 |
| 临时/中间结果 | 不定 | 不定 | 是 | 是 |

### 运行环境

- **OS**：Windows 10/11 或 Windows Server
- **文件系统**：NTFS（当前）
- **存储介质**：机械硬盘（HDD）+ 固态硬盘（SSD）混合，各工位配置不同
- **运行周期**：7×24 长期连续运行，现场无人值守
- **网络**：单机部署，无共享存储

## 现有问题诊断

现场长期运行偶发数据保存卡顿，可能根因为以下多方面因素叠加：

1. **NTFS 元数据碎片化**：长期高频创建/删除小文件导致 MFT（Master File Table）膨胀和碎片化，目录枚举性能退化
2. **$LogFile 写放大**：NTFS 每次元数据变更需先写 $LogFile，大量小文件创建/写入产生显著写放大（WAF 1.5–3×），参见 [[wiki/concepts/write-amplification.md]]
3. **SSD GC 毛刺**：SSD 垃圾回收（Garbage Collection）在写入压力下产生周期性延迟峰值，写放大（WAF 2–5× FTL 层）加速 SSD 磨损，参见 [[wiki/concepts/wear-leveling.md]]
4. **HDD 随机写**：机械硬盘的随机 I/O 性能极差（∼5K IOPS vs SSD ∼500K IOPS），目录结构遍历和碎片化小文件读取导致寻道延迟
5. **应用层积压**：异常流量下数据产生速率超过落盘速率，内存在数据积压，最终触发连锁卡顿
6. **分页溢出（Page Overflow）**：大量脏页未及时刷盘导致内存压力，引发系统级写节流

## 核心需求

### R1：可读的目录结构（可视化）

**优先级**：P0（必须）

存储方案必须对外呈现清晰的层级目录结构。现场运维人员通过文件资源管理器即可直接浏览检测数据，无需专用工具。这意味着不能采用纯 KV/对象存储（如 LevelDB/RocksDB 的纯扁平键值模型），必须在文件系统层保持目录树可见性。

**验收标准**：
- 通过 Windows Explorer 可完整浏览数据目录树
- 支持标准文件操作（复制、粘贴、拖拽）
- 目录结构符合项目定义的层级规范

### R2：冷热数据分级管理

**优先级**：P0

不同数据有不同的保留周期和访问频率：

| 热度 | 数据类型 | 保留时长 | 访问模式 |
|------|---------|---------|---------|
| 热数据 | 当前检测车辆的图像/JSON | 检测进行中（∼5 分钟） | 高频读写 |
| 温数据 | 今日已完成车辆数据 | 1–30 天 | 中等频率读取 |
| 冷数据 | 历史归档车辆数据 | 30–365 天 | 低频读取 |
| 过期数据 | 超过保留周期的临时数据 | N/A | 需自动清理 |

**验收标准**：
- 热数据路径写入延迟 P99 < 10ms（SSD）
- 冷数据自动迁移至 HDD / 归档区，对应用层透明
- 过期数据自动清理，清理策略可配置
- 冷热迁移不阻塞当前写入流

### R3：异常场景数据完整性保证

**优先级**：P0

现场可能发生：突然断电、系统蓝屏（BSOD）、磁盘满、应用崩溃、硬件故障。存储系统必须保证**已经确认落盘的数据不丢失、不损坏**。

**关键场景**：
| 异常场景 | 要求 |
|---------|------|
| 写入中途断电 | 文件数据完整（atomic write），不出现半写文件 |
| 系统蓝屏重启 | 文件系统可自动恢复，无数据损坏（类似 NTFS $LogFile 恢复） |
| 磁盘满 | 提前预警，拒绝写入并返回明确错误码，不静默丢失数据 |
| 应用崩溃 | 未完成写入的文件可通过崩溃一致性恢复或回滚 |

**参考机制**：
- [[wiki/concepts/copy-on-write.md]] @based_on — CoW 提供原子写入保障，崩溃后旧数据完整
- NTFS $LogFile 元数据日志 — 元数据操作可回滚

**验收标准**：
- 模拟断电测试 ≥ 100 次，数据完整性 100%
- 异常恢复后应用层可通过校验和（checksum）验证文件完整性

### R4：异构文件大小高效处理

**优先级**：P0

文件大小跨度极大：最小 JSON（1 KB）到最大点云（500 MB），相差 500× 以上。需要在同一目录树下高效处理。

**关键挑战**：
- 小文件（< 4KB）：碎片化严重，MFT 内部驻留 vs 外部存储的选择影响性能
- 大文件（> 100MB）：需要顺序写入优化，减少碎片
- 混合 I/O：小文件元数据和小数据 I/O 不能阻塞大文件的顺序 I/O

**验收标准**：
- 1 KB 文件写入延迟 P99 < 5ms（SSD）
- 500 MB 文件写入吞吐 ≥ 200 MB/s（SSD）
- 混合负载下（50% 小文件 + 50% 大文件）各指标退化 < 20%

### R5：目录结构查询效率

**优先级**：P1

应用按层级遍历目录查询数据，例如：
1. 列出某项目下所有车辆（第一层目录枚举）
2. 列出某车辆所有拍照点（第二层目录枚举）
3. 列出某拍照点所有照片（第三层文件枚举）

当车辆累积到数千辆、文件总数达到百万级别后，目录枚举性能不能退化到秒级。

**验收标准**：
- 单层目录枚举（含 ≤ 10,000 条目）完成时间 < 100ms
- 十万级文件总量下，三层目录深度遍历完成时间 < 500ms
- 查询性能不随总数据量线性增长（通过索引或扁平化策略）

### R6：海量元数据碎片分析与管理

**优先级**：P1

长期运行后，需要可观测、可分析的元数据状态：

- 当前存储了多少文件？总容量？各类型占比？
- 碎片化程度如何？是否存在大量 < 4KB 的碎片？
- 哪些目录占用了最多的 inode/MFT 条目？
- 是否存在异常（如某个目录文件数远超预期）？

**验收标准**：
- 提供元数据统计面板（CLI 或 API），展示上述指标
- 支持碎片化分析和整理建议
- 支持设置目录文件数阈值告警

### R7：数据积压优雅处理

**优先级**：P1

当应用层写入速率超过存储设备实际处理能力时（超规格保存数据），系统必须**优雅降级**而非崩溃或丢失数据。

**处理策略**：
1. **背压（Backpressure）**：写入接口返回延迟/排队信号，应用层感知并限流
2. **写缓冲**：内存缓冲吸收突发写入，异步刷盘
3. **降级写入**：必要时降低数据持久化保证（如临时允许写入未 fsync 的数据，尽快补齐）
4. **拒绝服务保护**：磁盘使用率达到阈值（如 85%）主动告警，95% 时拒绝写入，防止彻底用尽

**验收标准**：
- 突发 3× 正常写入速率持续 5 分钟，系统不崩溃
- 积压数据在 30 分钟内完全消化
- 积压期间已确认落盘数据 0 丢失

### R8：避免分页溢出（Page Overflow）

**优先级**：P1

当前方案中，大量脏页未能及时刷盘可能触发 Windows Memory Manager 的写节流（Write Throttling），表现为全局 I/O 卡顿。新方案需避免这种情况。

**技术方向**：
- 控制应用层缓冲脏页总量（直接 I/O 或 O_DIRECT 等效）
- 使用预分配 + 顺序写入减少 NTFS 文件碎片造成的元数据压力
- 监控 Memory Manager 脏页比例，主动触发放大刷盘

**验收标准**：
- 长时间运行（≥ 72h）下系统可用内存稳定在 20% 以上
- 无系统级写节流事件（通过 ETW Microsoft-Windows-Kernel-Memory 事件确认）

### R9：数据可靠性分级

**优先级**：P1

并非所有数据都需要相同的可靠性保证：

| 可靠性等级 | 数据类型 | 要求 |
|-----------|---------|------|
| 关键数据 | 原始图像、检测结果 JSON | 不可丢失，需多副本或校验和 |
| 普通数据 | 点云数据 | 可容忍偶发丢失（可重采） |
| 临时数据 | 中间计算结果 | 可丢失，崩溃后无需恢复 |

**验收标准**：
- 关键数据路径提供 fsync / FlushFileBuffers 等价保证
- 普通数据可在写入时指定 relaxed durability flag
- 临时数据写入崩溃后自动清理

### R10：稳定且高效的写入性能

**优先级**：P0（综合目标）

这是 R1–R9 的综合目标：在各种条件下保持写入稳定性和效率。

**量化指标**：
| 指标 | 目标值（SSD） | 目标值（HDD） |
|------|-------------|-------------|
| 稳态写入吞吐 | ≥ 300 MB/s | ≥ 150 MB/s |
| 写入延迟 P99 | < 10 ms | < 50 ms |
| 写入延迟 P999 | < 50 ms | < 200 ms |
| 最大卡顿时间 | < 200 ms | < 1 s |
| 7×24 运行稳定性 | 无 ≥ 1s 的写停顿 | 无 ≥ 5s 的写停顿 |

## 技术约束

| 约束项 | 说明 |
|--------|------|
| **OS 平台** | Windows 10/11（客户端）或 Windows Server，不可切换到 Linux |
| **文件系统兼容** | 最终存储需对 Windows 资源管理器可见（不一定是标准文件系统，可以是虚拟盘或用户态转发层） |
| **部署形态** | 单机，非分布式。无需考虑网络分区、多节点一致性 |
| **硬件** | 混合配置：部分工位纯 HDD，部分 SSD+HDD。方案需适配不同配置 |
| **无 GPU 依赖** | 存储引擎本身不依赖 GPU，不与应用层检测算法争抢 GPU 资源 |
| **开发语言偏好** | C/C++（内核态或用户态驱动）或 C#（用户态服务）——待决策 |
| **成本约束** | 软件方案为主，不强制要求特定硬件 |

## 方案方向探索

以下方案方向待可行性分析后收敛：

| 方向 | 思路 | 优势 | 挑战 |
|------|------|------|------|
| **A. NTFS 优化方案** | 在现有 NTFS 上做应用层优化：WAL + 分组写入 + 预分配 | 改动最小，兼容性最好 | 受限于 NTFS 本身设计，优化天花板低 |
| **B. 用户态文件系统** | 使用 Windows Projected File System (ProjFS) 或自定义用户态存储引擎 | 灵活度高，可自建索引 | 开发复杂度高，需处理缓存一致性 |
| **C. ReFS 迁移** | 将数据盘格式化为 ReFS，利用 CoW 和块克隆特性 | 数据完整性更好，CoW 写放大优化，参见 [[wiki/concepts/copy-on-write.md]] | ReFS 在客户端 Windows 上受限，兼容性需验证 |
| **D. 内核态 Minifilter** | 开发 Minifilter 驱动拦截文件 I/O，实现自定义缓存和聚合写 | 透明、高性能 | 开发难度最高，BSOD 风险 |
| **E. 混合存储引擎** | 用户态自研引擎 + 文件系统接口层（类似 SQLite 但目录可见） | 最灵活，可深度优化 | 生态孤岛，维护成本高 |

**决策待进行**：需结合 Wiki 层知识（存储栈、文件系统对比、性能工具链）做技术预研后收敛。
